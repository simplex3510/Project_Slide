# 코어 전투 시스템 기획서 (확정본)

> 본 문서는 대화를 통해 확정된 내용만 포함합니다. 미확정/검토 필요 사항은 별도로 표기했습니다.

---

## 1. 게임 기본 정보

- **장르**: 로그라이크-소울라이크 RPG
- **시점**: 탑뷰(Top-view)
- **이동**: WASD 상하좌우 이동 (게임 '아이작' 시리즈 참고)
- **공격**: 스킬 블록 조작으로 결정
- **전투 진행 방식**: 항상 **실시간**으로 진행됨. 스킬 블록 선택/드래그 중에도 게임은 일시정지되지 않으며, 캐릭터 이동/피격/적 행동이 계속됨.

---

## 2. 전투 UI 구조 — 스킬 블록 슬롯

- 화면 우측에 세로형 스킬 블록 슬롯(bar) 존재
- 스킬 블록은 위 → 아래 방향으로 낙하하며 슬롯에 누적됨
- **슬롯 최대 용량**: 8개 (임시 수치, 추후 확정 예정)

### 블록 생성 규칙
- 스킬 종류별로 개별 생성 확률이 존재
- 해당 확률에 따라 랜덤하게 블록이 생성되어 낙하

---

## 3. 블록 사용 방식

| 조작 | 소비 블록 수 | 결과 |
|---|---|---|
| 탭(클릭) | 1개 | 해당 스킬 1단계 발동 |
| 드래그(다중 선택) | 최대 3개 | 선택 개수 = 강화 단계 (2개→2단계, 3개→3단계) |

### 드래그(체이닝) 조건
- **슬롯 내에서 서로 인접한 동일 종류 블록만** 체이닝(다중 선택) 가능
- 최대 3개까지 연속 선택 가능
- 드래그 도중(선택 중) 마우스 버튼을 떼지 않고 취소하면 → **스킬은 사용되지 않고 드래그만 취소됨**
- 참고 레퍼런스: 크루세이더 퀘스트

---

## 4. 자원(마나, 가칭) 시스템

- 스킬 블록을 사용할 때마다 자원(마나, 가칭)이 생성/누적됨
- 자원이 특정 임계치에 도달하면 **전부 소모**하여 **특수 스킬(궁극기) 블록 1개** 생성
- 생성된 특수 스킬 블록은 **별도 슬롯이 아닌, 기존 낙하 슬롯에 동일하게 배치됨**

---

## 5. 보유 스킬 목록

슬롯에 낙하하여 쌓이는 블록은 총 **4종류**로 구성됨.

| 스킬 종류 | 체이닝 여부 | 강화 단계 | 비고 |
|---|---|---|---|
| 일반 공격 (= 스킬1) | O | 1~3단계 | |
| 스킬2 | O | 1~3단계 | |
| 스킬3 | O | 1~3단계 | |
| 특수 스킬 | X (체이닝 불가) | 1단계 고정 | 강화는 추후 스킬트리/패시브 연계 시스템에서 별도 진행 예정 |

> 참고: 초기 UI 프로토타입 이미지의 슬롯 표기("스킬2, 스킬2, 스킬3, 스킬1")는 실제 스킬 구성과 무관한 목업 표기였으나, 결과적으로 스킬 종류 수(4종)와는 일치함. 이미지의 "스킬1"은 정식 명칭 "일반 공격"으로 통일.

## 6. 스킬 사용 중 피격 판정 로직

### 6-1. 즉시 발동형 스킬 (모션 없음)
- "발동 중"이라는 시간 구간 자체가 존재하지 않음
- 사용 즉시 확정 처리 (취소 개념 미적용)

### 6-2. 모션이 존재하는 스킬
모션 내에 **"사용된 것으로 간주하는 기준 프레임(시점)"**을 하나 설정하여, 그 프레임을 기준으로 피격 시 처리가 갈림.

| 상황 | 블록 소멸 여부 | 피격 여부 | 결과 |
|---|---|---|---|
| 기준 프레임 **도달 전** 피격 | 소멸 안 됨 | 피격됨 | 스킬 발동 취소, 블록은 슬롯에 그대로 유지 → **즉시 재사용 가능** |
| 기준 프레임 **도달 후** (발동 중/완료) 피격 | 소멸됨 | 피격됨 | 스킬 정상 사용 처리, 블록 소모 + 피격 동시 적용 |

> 기준 프레임의 구체적인 수치(모션 내 정확히 몇 프레임째인지)는 추후 스킬별 모션 제작 단계에서 개별 지정하는 실무 사항이며, 현재 기획 단계에서는 "구간 분리 원칙"만 확정.

> 참고 사례: 몬스터 헌터의 슈퍼아머(하이퍼아머) 개념과 구조적으로 유사 — 모션을 선딜레이(캔슬 가능) / 판정(강행) 구간으로 나누는 방식.

## 7. 캐릭터 방향 스프라이트 & 판정 아키텍처

### 7-1. 캐릭터 바디 스프라이트 — 4방향 체계

| 방향 | 처리 방식 |
|---|---|
| 하(정면) | 별도 스프라이트 |
| 상(후면) | 별도 스프라이트 |
| 측면 | 별도 스프라이트 1벌 + `SpriteRenderer.flipX`로 좌/우 겸용 |
| 대각선 입력 | 가장 가까운 방향(상/하/측면)으로 스냅 처리 |

- 기존 확정된 Facing 로직(이동 중 = 입력 방향, 정지 중 = 마지막 방향)의 벡터값을 4방향 중 가장 가까운 방향으로 매핑하는 함수 필요 (예: `GetSnappedDirection(Vector2 facing) → enum {Down, Up, Side}` + `flipX` 여부)
- 대기·이동·피격·사망 등 **공통 모션**에 적용되는 기준. 심플 실루엣 픽셀 아트 스타일 기준으로 리소스 부담이 상대적으로 낮음을 전제로 확정.

### 7-2. 공격/스킬 판정 및 이펙트 — 코드 기반 회전 하이브리드

- 근접 판정 히트박스, 투사체, VFX는 방향별 전용 애니메이션을 별도 제작하지 않고, **공격 방향 벡터를 기준으로 코드에서 회전·배치**하여 처리
  - 근접 판정: 부채꼴/박스 형태 히트박스를 공격 방향 벡터에 맞춰 코드에서 회전·배치
  - 투사체: 스폰 시 velocity를 입력 방향으로 설정, 스프라이트는 `Transform.rotation`으로 회전
  - 이펙트(VFX): 동일하게 방향 벡터에 맞춰 회전 적용
- 스킬별 이펙트/판정 리소스는 **스킬당 1세트만** 제작하며, 방향 대응은 런타임 회전으로 커버(무제한 각도)
- 결과적으로 **바디 방향 인지(4방향 스냅)**와 **전투 판정 정밀도(무제한 각도 회전)**를 분리하여, 리소스 비용과 방향성 체감을 동시에 확보하는 구조
- 참고 사례: Enter the Gungeon, Nuclear Throne 등 탑뷰 액션 게임의 무기/이펙트 회전 처리 방식과 구조적으로 유사
