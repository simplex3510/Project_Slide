# Git 컨벤션

> Conventional Commits(https://www.conventionalcommits.org/) 를 기반으로 프로젝트에 맞게 조정한 규칙입니다.
> (구 `Commit Convention.md`에서 이름 변경 및 이슈 컨벤션 추가 — v3 참고)

---

# 1부. 커밋 메시지 컨벤션

## 1-1. 기본 형식

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `body`, `footer` 모두 **필수**로 작성합니다.
- `subject`는 한글 명령형으로, 마침표 없이 작성합니다.

## 1-2. type 목록

| type | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `perf` | 성능 개선 |
| `docs` | 기획서, README 등 문서 수정 |
| `style` | 포맷팅, 세미콜론 등 로직과 무관한 변경 |
| `test` | 테스트 코드 추가/수정 |
| `chore` | 빌드 설정, 패키지, 프로젝트 세팅 등 잡무성 작업 |

## 1-3. scope 목록 (프로젝트 도메인 기준)

| scope | 대상 |
|---|---|
| `movement` | 캐릭터 이동 로직 |
| `camera` | 카메라 추적/줌/흔들림 등 |
| `skill-block` | 스킬 블록 낙하, 체이닝(드래그), 슬롯 조작 등 **조작/로직** |
| `skill` | 개별 스킬 데이터, 모션, 이펙트 |
| `resource` | 자원(마나) 생성·누적·소모, 특수 스킬 생성 로직 |
| `hit` | 피격 판정, 기준 프레임 처리 |
| `ui` | 슬롯 등 전투 UI의 **시각적 표현/레이아웃** (skill-block과 구분: 로직이 아닌 뷰) |
| `core` | 여러 시스템에 걸친 아키텍처성 작업 |

> 멀티플레이(NGO) 관련 작업을 실제로 시작하는 시점에 `network` scope를 추가합니다.

> scope가 애매하면(예: 이동과 카메라를 동시에 건드림) 커밋을 분리하는 것이 원칙입니다.

## 1-4. subject 작성 규칙

- 50자 이내
- "무엇을 했는지"를 명령형으로 작성 (예: "추가", "수정", "제거" — "~함", "~했음" 지양)
- 마침표(.) 사용하지 않음

## 1-5. body 작성 규칙 (필수)

- 최소 1줄 이상, **"무엇을"보다 "왜"**에 집중해서 작성
- 배경, 의도, 기획 결정 근거 등을 남김
- 기획서의 특정 조항과 연관된 변경이라면 문서명/버전 정도만 간단히 언급 가능
  - 예: `시스템_기획서.md v5 기준 반영`

## 1-6. footer 작성 규칙 (필수) — 이슈 번호

모든 커밋은 관련된 GitHub 이슈 번호를 footer에 남깁니다.

- 작업이 완료된 커밋: `Closes #12` → push 시 해당 이슈가 자동으로 닫힘
- 작업이 진행 중이거나 참고만 하는 커밋: `Refs #12`
- **판단 기준**: 연결된 이슈 본문의 체크리스트(§2-2)가 **전부 체크된 상태를 만드는 커밋**일 때만 `Closes`를 사용합니다. 체크리스트 일부만 완료시키는 커밋은 반드시 `Refs`를 사용합니다.

## 1-7. 커밋 예시

**좋은 예:**
```
feat(skill-block): 스킬 블록 드래그 체이닝 로직 구현

슬롯 내 인접한 동일 종류 블록을 최대 3개까지 연속 선택할 수 있도록 구현.
드래그 도중 취소 시 사용 없이 선택만 취소되도록 처리하여
실수로 인한 스킬 낭비를 방지함.

Closes #14
```

```
fix(camera): 이동 중 카메라 떨림 현상 수정

Camera Follow 갱신 타이밍을 FixedUpdate에서 LateUpdate로 변경.
캐릭터 물리 갱신과 카메라 갱신 시점이 어긋나서 발생한 문제였음.

Closes #21
```

**지양할 예:**
```
update stuff
```
```
feat(movement,camera): 이동이랑 카메라 같이 손봄
```
(→ scope가 두 개 필요하다는 것은 커밋을 나눠야 한다는 신호)

# 2부. 이슈(Issue) 컨벤션

## 2-1. 라벨을 통한 type/scope 관리

이슈 제목은 프리픽스 없이 **작업 내용 설명에만 집중**하고, type과 scope는 **GitHub Label**로 관리합니다.

- 라벨 네임스페이스는 커밋 컨벤션의 type(§1-2)/scope(§1-3) 목록을 그대로 재사용하되, 다음과 같이 접두어를 붙여 구분합니다.
  - `type: feat`, `type: fix`, `type: refactor`, `type: perf`, `type: docs`, `type: style`, `type: test`, `type: chore`
  - `scope: movement`, `scope: camera`, `scope: skill-block`, `scope: skill`, `scope: resource`, `scope: hit`, `scope: ui`, `scope: core`, `scope: network`
- 이슈 하나에 `type` 라벨 1개, `scope` 라벨 1개 이상을 부여합니다.
- **대표 라벨 원칙**: 이슈의 라벨은 "이 이슈가 다루는 작업의 대표 성격"을 나타내는 것으로, 하위에서 발생하는 개별 커밋들의 scope와 1:1로 일치할 필요는 없습니다. 하나의 이슈를 진행하며 여러 scope의 커밋이 `Refs`로 걸리는 것은 정상적인 흐름입니다.
- 라벨은 최초 1회 아래와 같이 생성해두고, 이후에는 이슈 생성 시 선택만 하면 됩니다.

```bash
# type 라벨 예시 (gh CLI)
gh label create "type: feat" --color "0E8A16"
gh label create "type: fix" --color "D93F0B"
gh label create "type: docs" --color "0075CA"
# ... 나머지 type/scope도 동일한 방식으로 생성
```

> 라벨 색상은 자유롭게 정하되, type 계열과 scope 계열을 서로 다른 색상 톤으로 구분해두면 이슈 목록에서 스캔하기 쉽습니다.

## 2-2. 이슈 본문 템플릿 (고정)

모든 이슈는 아래 구조를 따릅니다.

```
## 배경
(왜 이 작업이 필요한지 — 의도/맥락)

## 작업 내용
- [ ] 작업 항목 1
- [ ] 작업 항목 2

## 참고
(관련 기획서명 + 버전, 관련 이슈/PR 번호 등)
```

- **작업 내용**은 반드시 체크리스트 형식으로 작성합니다. 이슈에 여러 커밋이 `Refs`로 걸릴 때 진행률을 한눈에 파악하기 위함이며, §1-6의 `Closes`/`Refs` 판단 기준의 근거가 됩니다.
- **참고** 항목은 비어있어도 무방하나, `type: docs` 라벨이 붙은 이슈(§2-3)는 필수로 작성합니다.

## 2-3. 기획서 연동 이슈의 특수 규칙

`type: docs` 라벨이 붙은 이슈, 즉 기획서 개정 자체가 작업 대상인 이슈는 본문의 **참고** 항목에 관련 기획서명과 버전을 반드시 명시합니다.

- 예: `참고: 시스템 기획서.md v5 반영`

## 2-4. Closes / Refs 판단 기준 (이슈 쪽 대칭 규칙)

- 이슈 본문의 작업 내용 체크리스트가 **전부 체크된 상태를 만드는 커밋**만 `Closes #n`을 footer에 사용할 수 있습니다.
- 체크리스트가 일부만 완료된 상태라면, 해당 이슈에 연결되는 모든 커밋은 `Refs #n`을 사용합니다.
- 이 기준은 §1-6(커밋 쪽 규칙)과 대칭되며, 커밋 메시지 작성 시점과 이슈 진행 상태를 항상 함께 확인합니다.
